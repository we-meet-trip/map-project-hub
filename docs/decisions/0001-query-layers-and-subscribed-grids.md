# 0001. 조회 3계층과 구독 격자 폴링

## 맥락
날씨·장소·경로 자료는 외부 API 에서 온다. 화면을 열 때마다 외부 API 를 부르면 발급처가 느리거나 멈출 때 화면이 같이 느려지거나 실패하고, 호출량이 사용자 수에 비례해 늘어 발급처 한도를 넘는다. 기상청 단기예보는 격자(5km)마다 따로 받아야 해서 전국을 다 받을 수도 없다.

## 선택지
1. 요청 때마다 외부 API 를 부른다.
2. 외부 응답을 캐시만 한다.
3. 날씨는 정해 둔 격자만 주기적으로 받아 DB 에 두고, 조회는 DB 만 읽는다. 나머지 자료는 키별 캐시를 둔다.

## 결정
3. 조회는 Redis 캐시 → PostGIS 적재본 → 외부 API 세 층으로 나눈다. 날씨는 구독 격자(시군구 대표 좌표, 같은 격자는 한 번만)만 폴링하고, 조회 요청은 같은 광역 안에서 가장 가까운 활성 구독 격자로 답한다.

## 결과
- 날씨 조회는 발급처 상태와 무관하게 빠르고, 발급처가 멈춰도 직전 적재분으로 답한다.
- 적재 격자와 조회 격자가 어긋나면 빈 값이 나오는 위험이 생겨, 격자 선택 규칙을 실제 시드 좌표로 시험에 고정했다([troubleshooting.md](../troubleshooting.md) T-WEATHER-01).
- 구독 격자는 관리 콘솔에서 켜고 끈다.
